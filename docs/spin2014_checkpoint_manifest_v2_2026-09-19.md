# 检查点大规模证据清单修复：v2

## 本轮结论

已实现并验证大清单存储修复。上轮 G7 在第一阶段后因 `CHECKPOINT_HEADER_LIMIT` 退出的故障，可在 v1 重现；同一原始阶段 payload 使用 v2 可完整保存并在新进程重读。

这不是新的 G7 优化实验，也不证明 G7 收敛。旧结果仍为 `PROCESS_FAILED / INCOMPLETE_JOB`，最终几何、二值验证、仿真、原论文复现状态没有升级。

新证据目录：`build/spin2014-checkpoint-v2-20260919`。

## 设计与兼容性

- 新增显式导入的 `source_checkpoint_store_v2.StageCheckpointStore`；v1 源码及上轮 runner、spec、协议、构建产物均未修改。
- v2 继续使用 `SPCKPT01` 二进制帧布局，但 JSON schema 为 `source-stage-storage-v2`，不是 v1。
- 完整身份清单保存为 `identity-<SHA256>.json`，默认独立上限 16 MiB（显式配置硬上限 64 MiB）；检查点仍保持原来的 1 MiB 头部上限。两者是不同对象、不同容量限制。
- 清单保留全部标签、真实路径、大小、SHA-256；阶段头部只保存清单文件名、摘要、大小和条目数。
- 每次读取/发布均重新检查原始依赖文件及符号链接目标，不会仅验证清单文件本身。被引用清单缺失、损坏、替换为符号链接或引用被篡改均拒绝，不自动补回。
- 顺序为：清单文件同步与目录同步 → 阶段文件同步与目录同步 → 提交收据同步与目录同步。中断证据保留；不替换已有记录。
- v1、v2 链互相拒绝。旧结果只能用明确的 v1 读取器访问，不自动迁移，不允许混写。

仍沿用 v1 的私有本地目录、POSIX flock/link/fsync、外部文件在操作期间不可变的前提。这是完整性载体，不是防恶意篡改的认证日志。检查点内的计数仍由调用者报告，不能替代实验资源监督器。

## 启动前容量检查

构造 v2 存储时，先对实际清单执行容量检查；超限时不创建存储目录。

`preflight(artifact_paths=...)` 可对尚未生成的全部计划 trace 路径计算最坏字段宽度的头部上界。调用者必须在启动优化前传入完整阶段集合；仅构造存储、不传入路径，只完成基础头部检查，不能据此承诺未来所有阶段容量足够。发布时仍执行实际文件和实际头部容量检查。

正式新 G7 runner **尚未切换到 v2 或启动**。当前预检使用真实候选配置中全部 24 个阶段的固定预期路径，作为容量验证；下一批必须对其自身最终工作路径重新预检并绑定 v2 模块。
